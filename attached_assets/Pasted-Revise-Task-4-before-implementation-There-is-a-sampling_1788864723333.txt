Revise Task #4 before implementation. There is a sampling-bias problem in the current design.

The proposed three-query sample (totalUsers, newest, lastUpdate, max 1,000 each) is not sufficient to calculate:

true Actor supply per cluster
provider concentration / HHI
cluster usage percentiles
meaningful supply thinness

Those metrics would be systematically biased because Actors outside those three sampled result sets would be invisible.

For Discovery Scout v0, prefer a complete public Apify Store catalog snapshot if the API allows deterministic pagination through the full Store at zero monetary cost.

Fetching the entire public Store catalog through pagination, approximately 1 request per 1,000 Actors.
Recording the actual total count and verifying that the run obtained complete coverage before computing supply/concentration metrics.

Do not make three duplicate 1,000-record ranking queries if a single paginated catalog traversal can provide the underlying Actor fields needed for scoring.
Keep request pacing extremely conservative despite the generous documented limits.
Separate:
current catalog structure
change between our own snapshots
source metadata such as 7/30/90-day users
