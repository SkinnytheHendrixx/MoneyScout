## C41-16 — `R12 → R3`

R12 explicitly schedules R3 evidence-freshness rechecks while preserving the rule that the upstream domain owns what result would satisfy the obligation. R3, however, allows one evidence object to be shared across multiple Opportunities, Evaluation Cycles, factors, and freshness policies, and explicitly forbids one consumer's freshness result from globally stamping the evidence fresh for another use.

R12's generic domain-obligation/runnable-occurrence separation is not by itself enough to prove which exact R3 revalidation target an occurrence represents. C32-03 established the standing rule that when a runnable occurrence represents an authoritative upstream object, the occurrence must bind the exact upstream object/version rather than merely the general class of work.

### Proposed required strengthening — exact R3 revalidation-target binding

> **Every R12 runnable occurrence materialized for an R3 freshness revalidation must durably bind the exact authoritative R3 revalidation target/identity or fingerprint it represents, including enough immutable consumer context to distinguish the exact evidence/snapshot, Opportunity/Evaluation lineage or other governed consumer identity, applicable freshness policy/version, and decision use whose freshness must be reevaluated. A generic `revalidate evidence E` occurrence is insufficient when E is shared across materially different policy/consumer contexts.**

Required fixture:

1. Evidence E is shared by consumers C1 and C2.
2. C1 uses freshness policy P1 for a current pricing decision; C2 uses P2 for a historical/slow-changing decision.
3. R12 occurrence Q1 is created for C1/P1 revalidation of E.
4. Process dies and Q1 is reconstructed.
5. Q1 must still identify C1/P1/E, not merely E or the currently active consumer/policy.
6. A fresh result under C2/P2 cannot satisfy Q1.
7. A P1 policy-version change that materially changes the revalidation target must be represented as a governed successor/version rather than silently mutating Q1's meaning.
8. Cycle/current-state changes cannot rebind Q1 to a new R4 lineage.
9. Repeated recovery converges on one occurrence for the same exact revalidation target.
10. The resulting R3 freshness result remains owned by R3 and does not itself create R20 authority.

This is not `MISSING_REQUIRED_COMPOSITION`: R12 explicitly names R3 rechecks. The gap is exact scheduled-target correspondence.

**Provisional disposition:** `CONSISTENT_CONSUMPTION` with required exact-R3-revalidation-target strengthening.

## C41-20 — `R18 → R5`

**Primary:** `CONSISTENT_CONSUMPTION`

R18 explicitly states that provider-family equivalence materially affecting substitution authority is subject to R5 unless the proposition is fully reducible to authoritative deterministic facts. R18 also correctly states that even confirmed equivalence does not itself authorize substitution unless the governing execution contract permits it.

R5's generic exact-candidate machinery supplies independent-confirmation semantics, but R18 does not define the exact candidate identity dimensions that make a provider-family/binding-equivalence proposition complete. ### Proposed required strengthening — R18-specific exact equivalence-candidate binding

> **Whenever an R18 capability-binding validation, rebinding/successor decision, or contract-permitted substitution path materially relies on an R5-governed provider-family/binding-equivalence conclusion, the consumed R5 confirmation must bind the exact equivalence proposition being relied upon: the exact originating binding/provider/account/claim/scope, proposed provider/account/binding alternative, governing execution/operation class, applicable verification/lifecycle policy context, evidence snapshot, candidate fingerprint, and the precise authority question for which equivalence is asserted. A generic `provider B is equivalent to provider A` conclusion is insufficient.**

Required fixture:

1. Execution X is frozen to binding B1 = provider A/account A1/claim C/scope S.
2. A contract-permitted successor/rebinding path proposes B2 = provider B/account B1.
3. Material equivalence candidate EQ1 asserts B2 is equivalent for the exact authority question at issue.
4. R5 confirmation binds exact B1, B2, claim/scope, operation class, policy/lifecycle context, evidence, and candidate fingerprint.
5. Change B2 to B3, account B1 to B2, scope S to S2, or policy/lifecycle conditions materially; EQ1 does not transfer.
6. Confirmation that providers are commercially/technically similar in general is insufficient.
7. If equivalence is deterministically provable from authoritative frozen facts, R5's deterministic-verifier allowance remains available.
8. `CHALLENGED`/`INCONCLUSIVE` blocks reliance on equivalence.
9. Even `CONFIRMED EQ1` does not authorize substitution unless the governing execution contract independently permits it.
10. Historical B1 execution identity remains intact; equivalence never rewrites past execution onto B2.

### Relation to C24-02

This is not a new systemic confirmation principle. C24-02 already established that domain-specific equivalence propositions must bind the exact material dimensions that make the candidate meaningful. C41-20 applies that standing rule to R18's provider-family/binding-equivalence seam. The edge still needs an R18-specific fixture so the existing governance cannot become invisible here.

This is not `MISSING_REQUIRED_COMPOSITION` and not an unresolved semantic gap: R18 explicitly requires R5 where material judgment is involved, and R5 already supplies the normative confirmation machinery.

**Provisional disposition:** `CONSISTENT_CONSUMPTION` with R18-specific exact equivalence-candidate strengthening/carry-forward of C24-02.
